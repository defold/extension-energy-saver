**“energy consumed by the engine” needs a precise definition**. Depending on the platform, you can obtain energy attributed to a process, energy used by a hardware component, or battery discharge for the entire device. Those measurements should remain distinguishable in the profiler.

Energy is measured in **joules (J)**; power is the rate of consumption in **watts (J/s)**.

For Defold’s main platforms, these are the relevant options:

| Platform | API / interface | What it provides | Main limitations |
|---|---|---|---|
| **macOS** | `proc_pid_rusage(pid, RUSAGE_INFO_V6, ...)`, particularly `ri_energy_nj`. On ARM, `task_info(..., TASK_POWER_INFO_V2, ...)` also exposes `task_energy`. | Process CPU energy accounting in nan joules, where implemented. Apple’s kernel connects these fields to its CPU energy accounting. | Hardware and OS support vary. This does not represent the app’s complete CPU + GPU + display + networking consumption. [Apple kernel implementation](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task.c) |
| **iOS / iPadOS** | Darwin task/resource APIs above are candidates requiring device validation; **MetricKit** provides the supported higher-level reporting framework. | MetricKit reports CPU time/instructions, GPU time and other activity associated with energy consumption. | MetricKit delivers daily aggregates, so it cannot drive a live watts display. Low-level energy counters need validation on the supported devices and OS versions. [MetricKit](https://developer.apple.com/documentation/metrickit), [Darwin resource fields](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/resource.h) |
| **Android 15+ / API 35+** | `SystemHealthManager.getSupportedPowerMonitors()` and `getPowerMonitorReadings()` | Cumulative energy from hardware power rails or modeled consumers. `getConsumedEnergy()` returns µW·s, equivalent to **µJ**, with a timestamp. | Device/component scope, including other apps. Hardware support is optional; enumeration can return an empty list. Readings include operation on battery and external power. [Manager API](https://developer.android.com/reference/android/os/health/SystemHealthManager), [readings API](https://developer.android.com/reference/android/os/PowerMonitorReadings) |
| **Android API 21+** | `BatteryManager.getLongProperty(BATTERY_PROPERTY_ENERGY_COUNTER)`; alternatively current properties plus battery voltage | Remaining battery energy in nWh; current in µA can support an estimate of battery power. | Entire battery/device. Properties may be unavailable. While charging, battery current measures net charging/discharging rather than total device consumption. [BatteryManager](https://developer.android.com/reference/android/os/BatteryManager) |
| **Linux** | Powercap/RAPL sysfs: `/sys/class/powercap/.../energy_uj` and `max_energy_range_uj` | Cumulative energy for CPU packages and available subdomains, such as cores or memory. | Hardware/domain support and read permissions vary. Includes all processes using that domain. Handle counter wraparound and avoid adding overlapping parent/child domains. [Kernel powercap documentation](https://cdn.kernel.org/doc/html/latest/power/powercap/powercap.html) |
| **Windows 10+** | **Energy Metering Interface (EMI)**: enumerate `GUID_DEVICE_ENERGY_METER`, then use `DeviceIoControl(..., IOCTL_EMI_GET_MEASUREMENT, ...)` | Accumulated energy and timestamps for hardware channels; documented energy units include picowatt-hours. | Requires compatible hardware and drivers. Measures the reported hardware domain rather than a particular process. [EMI documentation](https://learn.microsoft.com/en-us/windows-hardware/drivers/powermeter/energy-meter-interface) |
| **Windows laptops** | `Windows.Devices.Power.Battery.GetReport()` | Battery charge/discharge rate in mW and remaining energy in mWh. | Whole-device battery measurement; values can be unavailable. Charging has the same interpretation problem as Android. [BatteryReport](https://learn.microsoft.com/en-us/uwp/api/windows.devices.power.batteryreport) |
| **HTML5 / browsers** | `navigator.getBattery()` where implemented | Battery level, charging status and estimated remaining time. | No energy counter or watts measurement suitable for an engine profiler. [Battery Status specification](https://www.w3.org/TR/battery-status/) |

**The macOS option looks particularly promising:** I ran a small, unprivileged probe on your Mac. `proc_pid_rusage(..., RUSAGE_INFO_V6, ...)` succeeded, and `ri_energy_nj` increased during CPU work. That confirms a working counter on this machine; its accuracy and availability across other devices still need validation.

Desktop GPU vendors provide additional APIs:

| GPU | API | Measurement |
|---|---|---|
| **NVIDIA** | NVML: `nvmlDeviceGetPowerUsage()` and `nvmlDeviceGetTotalEnergyConsumption()` | Power in mW and, on supported devices, cumulative energy in mJ. These cover the GPU and associated circuitry. Some power readings are averaged over one second. [NVML documentation](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html) |
| **AMD** | Windows: ADLX `IADLXGPUMetrics::GPUTotalBoardPower()`. Linux: amdgpu hwmon `power1_average` / `power1_input`. | Board/component power, depending on the interface and hardware. Integrate power over time to estimate energy. [ADLX](https://gpuopen.com/manuals/adlx/adlx-sdk-references/adlx-interfaces/performance-monitoring/iadlxgpumetrics/gputotalboardpower/), [amdgpu](https://docs.kernel.org/gpu/amdgpu/thermal.html) |
| **Intel** | Level Zero Sysman: `zesPowerGetEnergyCounter()` | Energy in µJ and a timestamp for an exposed power domain. Requires a supporting driver/device. [Sysman documentation](https://oneapi-src.github.io/level-zero-spec/level-zero/latest/sysman/api/apis/power.html) |

These GPU readings generally include other workloads using the device.

There are also useful **external profiling routes**. macOS `powermetrics` reports estimated subsystem power and a relative process energy-impact score—the installed manual explicitly distinguishes the score from physical energy. Apple’s [Instruments Power Profiler](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler) supports iPhone/iPad power investigations. Android’s [Power Profiler](https://developer.android.com/studio/profile/power-profiler) exposes device power rails on supported Pixels. Windows provides app-attributed estimates through [E3 reports](https://learn.microsoft.com/en-us/shows/defrag-tools/157-energy-estimation-engine-e3) and [PowerSnap trace events](https://learn.microsoft.com/en-us/windows/win32/power/powersnap). These are useful for validating an engine implementation and investigating regressions.

I would start with the working **macOS process CPU counter**, **Android API 35 power monitors**, and **Linux RAPL**, then add optional desktop GPU backends. That would provide useful data while keeping the meaning of each measurement clear.
